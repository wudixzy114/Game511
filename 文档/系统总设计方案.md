# 系统总设计方案

## 1. 文档目的

本文档用于汇总《道》当前阶段的总体系统设计，明确项目真正要服务的体验目标、已经完成的技术底座、后续系统分层和下一阶段开发优先级。

---

## 2. 游戏设计锚点

《道》的核心不是传统开放世界任务清单，而是“世界规律驱动体验，征兆替代命令，历程本身成为宝藏”。玩家不应该被任务面板推着走，而应该在自然世界、预兆、遭遇和自我选择之间逐渐形成方向。

基于游戏介绍，系统设计必须遵守以下锚点：

- 不做传统任务模式。系统可以记录、回应和暗示，但不能把玩家变成执行清单的人。
- 不用传统数值成长作为核心奖励。玩家的变化主要体现在世界反馈、旅程记忆、遭遇结果和体验层次上。
- 程序化生成优先。地形、材质、地点、天气、征兆和遭遇都应尽量由规则生成，减少对手工资产的依赖。
- 世界规律优先于剧情脚本。叙事不是预写任务链，而是由地点、环境、玩家行为和征兆共同涌现。
- AI 可以增强个性化历险，但不应成为当前阶段的硬依赖。必须先建立可测试、可回放、可硬编码运行的导演接口。

---

## 3. 当前项目状态

当前项目已经完成第一层可运行底座，不再是空工程。

### 3.1 基础设施

已完成：

- Rust + Bevy 工程结构，分离 `core` 与 `game` 模块。
- 配置系统，集中管理窗口、世界、环境、玩家、征兆、展示模式和性能预算。
- 分层日志系统，包含应用日志、错误日志和性能日志。
- 帧性能采样与超预算告警。
- 自动退出烟雾验证路径。
- 基础单元测试与 `clippy -D warnings` 质量红线。

后续重点：

- 建立更明确的集成测试入口。
- 为较大系统补充可重复的展示场景和性能采样标签。

### 3.2 世界与地形

已完成：

- 程序化高度场、湿度、坡度、河流、侵蚀和沉积规则。
- 水域、草甸、林地、旷野、山脊等基础群系。
- 大型开放世界分块流式加载。
- mesh 与散布缓存。
- 后台地形生成、三层 LOD、近景碰撞代理、远景 impostor。
- 第一人称基于高度场的胶囊接触、坡度限制、台阶抬升和落差脱离。
- 程序化地表贴图与基础散布物。

后续重点：

- 将地形从“可走、可看”推进到“可识别、可记忆、可发生事件”。
- 增加具有意义的程序化地点，而不是继续只扩大地形复杂度。

### 3.3 环境视觉

已完成：

- 太阳、月亮、星空、雾、大气色调。
- 晴天、薄雾、降雨、暴风雨、降雪天气序列。
- 雨、雪、雾粒子与闪电光效。
- 展示模式可播放多个环境场景。

后续重点：

- 让天气与征兆、地点和旅程阶段发生关系。
- 让环境不只是背景，而是世界回应玩家状态的媒介。

### 3.4 征兆系统

已完成：

- `SignState` 管理共鸣、平静、当前位置上下文和征兆触发。
- 征兆判定已经接入群系、地势、昼夜和运动速度。
- 已有晨光、林语、峰召、静水等征兆类别。
- `OmenBeacon` 点光源提供基础可见反馈。

后续重点：

- 征兆需要从“触发一个光源”升级为“引导一段旅程”。
- 需要表达方向、强度、持续时间、误入歧途、接近目标和抵达后的回应。

### 3.5 玩家、UI 与生命周期

已完成：

- 主菜单、探索模式、展示模式、暂停、继续、重开、返回主菜单、退出程序完整生命周期。
- 探索模式第一人称控制。
- 展示模式自动导演。
- HUD 显示当前模式、时间、地貌、坐标、共鸣、平静和征兆。
- UI 使用系统中文字体，解决中文乱码。

后续重点：

- 当前 HUD 偏调试面板。正式体验需要减少数值感，保留开发调试开关。
- 需要加入“旅程记忆/回响”界面，记录玩家经历过的征兆和地点，但不能变成任务列表。

### 3.6 AI 个性化历险

当前状态：

- 尚未实现在线 AI。
- 现有工程已经具备世界、征兆、日志和生命周期边界，可支撑后续接入。

后续重点：

- 先实现确定性的“旅程导演接口”和硬编码回退逻辑。
- 再考虑接入 LLM 或其他 AI 生成层，避免在基础体验不稳定时引入高复杂度依赖。

## 4. 总体系统分层

下一阶段以后，项目应按以下分层演进。

### 4.1 Core 层

负责配置、日志、性能、错误、测试辅助、自动化验证。

要求：

- 所有新系统必须有配置入口或合理默认值。
- 所有可疑失败都要写日志。
- 关键纯逻辑必须有单元测试。

### 4.2 World 层

负责地形、群系、水系、散布物、程序化地点、碰撞代理和空间查询。

要求：

- 世界不只是渲染网格，还要提供“哪里适合发生什么”的查询能力。
- 未来地点、生态和遭遇都应依赖 `WorldMap` 或独立空间索引，而不是手写固定坐标。

### 4.3 Environment 层

负责昼夜、天气、天空、雾、粒子和环境光。

要求：

- 环境状态必须可被旅程导演和征兆系统读取。
- 环境变化可以成为征兆反馈的一部分。

### 4.4 Journey 层

下一阶段新增的核心层。负责玩家当前旅程状态、旅程阶段、内在倾向、已触达地点、已发生回响和可回放事件记录。

要求：

- 不提供传统任务目标。
- 只记录“经历”和“世界回应”。
- 必须可由确定性规则驱动，也要能在未来接入 AI 生成建议。

### 4.5 Places 层

下一阶段新增。负责程序化生成有意义的地点，例如古树、泉眼、山脊门、静水湾、石阵、孤火、遗迹残墙。

要求：

- 地点由世界规则筛选生成，不应固定写死在出生点附近。
- 地点要有可识别视觉轮廓、接近判定和可参与征兆判定的语义标签。

### 4.6 Omen 层

负责征兆判定、方向暗示、强度变化和表现触发。

要求：

- 征兆不是任务箭头。
- 可以通过光、雾、风、粒子、声音预留接口、远景轮廓、漫游体行为来引导。
- 需要与 Journey 和 Places 互相协作。

### 4.7 Interaction 层

负责玩家与世界的轻量交互。

要求：

- 第一阶段只做“靠近、停留、注视、聆听”这类低成本交互。
- 不急于做复杂物品、战斗和 NPC 对话。

### 4.8 UI 层

负责生命周期、暂停、设置、展示入口、开发 HUD、旅程记忆。

要求：

- 玩家正式 UI 应克制，避免任务面板化。
- 调试数据应保留，但后续需要开发模式开关。

### 4.9 Presentation 层

负责每个阶段的可重复展示。

要求：

- 每个大系统完成后都应有展示路径。
- 展示模式必须能覆盖新系统的关键效果。

---

## 5. 下一阶段判断

下一阶段不建议优先做在线 AI、复杂战斗、第三人称动画、完整生态或继续扩大地形技术。原因是这些都不能直接证明《道》的核心体验成立。

下一阶段最应该做的是：

### 第一段可玩旅程闭环

目标是让玩家从主菜单进入世界后，在没有任务面板的情况下，经历一段完整但短小的体验：

1. 玩家出生在世界中，自由移动。
2. 系统根据玩家位置、速度、平静度、时间和环境，选择一个适合的“意义地点”。
3. 世界通过征兆给出非命令式暗示。
4. 玩家接近地点后，通过停留、注视或聆听触发一次遭遇。
5. 天气、光照、漫游体或地貌细节产生回应。
6. 旅程记忆记录这次经历。
7. 玩家可以继续探索、暂停、重开或返回主菜单。

这个闭环是后续 AI 个性化历险、生态模拟、声音系统、叙事系统和更高级 UI 的共同基础。

## 6. 下一阶段模块建议

### 6.1 `journey.rs`

新增旅程系统，包含：

- `JourneyState`
- `JourneyStage`
- `JourneyMemory`
- `JourneyEvent`
- 当前目标地点引用，但不向玩家显示为任务
- 可测试的阶段推进逻辑

### 6.2 `places.rs`

新增意义地点系统，包含：

- `MeaningfulPlace`
- `PlaceKind`
- 地点候选筛选
- 地点实体生成和清理
- 地点接近判定

### 6.3 `signs.rs` 升级

将当前征兆扩展为可服务旅程的反馈系统：

- 征兆强度
- 征兆方向
- 征兆目标地点
- 接近目标时的变化
- 抵达地点后的回应事件

### 6.4 `ui.rs` 升级

保留当前生命周期 UI，同时新增：

- 开发 HUD 显示开关
- 旅程回响/记忆面板
- 暂停界面的旅程摘要

### 6.5 `presentation.rs` 升级

新增“第一段旅程展示”：

- 自动展示出生、征兆出现、接近地点、触发回应和记忆记录。
- 仍然支持 `DAO_PRESENTATION_MODE=1` 快速验证。

---

## 7. 当前优先级

1. 第一段可玩旅程闭环。
2. 程序化意义地点。
3. 征兆引导升级。
4. 旅程记忆 UI。
5. 展示模式覆盖新闭环。
6. 再继续扩展生态、角色行为树、声音系统和 AI 个性化导演。

---

## 8. 结论

《道》当前已经完成技术底座和可运行世界原型。下一步的关键不是再证明 Bevy 能画地形，也不是马上接入 AI，而是证明玩家在没有任务指令时，仍然能被世界自然牵引，完成一次有意义的经历。

因此，下一阶段开发应集中在“第一段可玩旅程闭环”：旅程状态、意义地点、征兆引导、轻交互、世界回应和旅程记忆。
