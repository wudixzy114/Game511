# 《道》质量要求

## 原则

1. 必须使用可靠、可维护的实现，不能用脆弱的临时方案替代。
2. 必须保持清晰的代码结构和错误处理，重要异常必须记录到日志。
3. 可以引入成熟的第三方库，但要符合项目风格和维护成本。
4. 性能不能无依据妥协；性能改动必须用工具验证。
5. 画面和交互不能有明显破损、遮挡、错位或无法完成的流程。
6. 模块应高内聚、低耦合，便于扩展和维护。

## 日志要求

1. 运行日志、错误日志、性能日志必须分开记录。
2. 日志文件只保留当前和上一次运行：

```text
logs/application.log
logs/application.log.1
logs/error.log
logs/error.log.1
logs/performance.log
logs/performance.log.1
```

3. 调查问题时应优先生成 HTML 日志视图：

```powershell
.\scripts\log.ps1
```

4. 日志查看应按类型、级别、系统 target、全文搜索过滤，避免只凭零散终端输出判断。

## 性能要求

1. 新模块或重型系统应接入性能埋点，使其能出现在性能报告中。
2. 性能报告入口：

```powershell
.\scripts\perf.ps1
```

3. 性能优化前必须先采集 baseline，优化后必须再次采集，并运行：

```powershell
.\scripts\perf.ps1 -Action compare
```

4. 性能优化的结论必须基于对比数据，不能只说“应该更快”。
5. 必须关注平均帧耗时、p95、p99、超预算帧数、主要瓶颈阶段。
6. 如果报告提示 `low instrumentation coverage`，说明埋点覆盖不足。此时应补充埋点或在结论中明确数据不足，不能把现有阶段直接当作完整瓶颈结论。

## 测试要求

1. 纯逻辑模块必须尽量写单元测试。
2. 非纯函数逻辑应通过集成测试、脚本、短时自动运行或日志/性能报告验证。
3. 收尾前通常运行：

```powershell
cargo fmt --all --check
cargo test
cargo clippy --all-targets -- -D warnings
```

## 编译和运行要求

1. 代码完成后必须保证没有编译错误。
2. clippy 警告按错误处理。
3. 需要验证游戏启动时，优先使用脚本：

```powershell
.\scripts\run-dev.ps1
```

或短时自动运行：

```powershell
$env:DAO_AUTO_EXIT_SECONDS = "1"
cargo run --bin dao_game
```
