# 性能工具使用说明

## 主要命令

日常只需要一个入口：

```powershell
.\scripts\perf.ps1
```

深度热点诊断使用：

```powershell
.\scripts\ultimate-profile.ps1
.\scripts\profile.ps1 -Mode tracy
.\scripts\profile.ps1 -Mode tracy-analyze
```

默认行为：

- 自动跳过主菜单，进入 `presentation` 展示模式。
- 运行 12 秒后自动退出。
- 使用日志系统的轮转文件生成 `logs/performance-report.html`。
- 不再额外复制性能日志快照，避免重复文件。

性能日志只保留：

```text
logs/performance.log
logs/performance.log.1
```

其中：

- `performance.log`：本次运行
- `performance.log.1`：上一次运行

## AI 必须遵守的性能优化流程

只要任务涉及性能优化，AI 必须执行：

1. 优化前采集 baseline：

```powershell
.\scripts\perf.ps1 -Seconds 12
```

2. 修改代码。

3. 优化后再次采集：

```powershell
.\scripts\perf.ps1 -Seconds 12
```

4. 运行对比：

```powershell
.\scripts\perf.ps1 -Action compare
```

5. 最终回复必须汇报对比结果，包括：

- 平均帧耗时变化
- p95 / p99 变化
- 超预算帧数变化
- 主要瓶颈阶段变化
- 是否出现 `low instrumentation coverage`

如果数据没有改善，必须明确说明“本次优化未被性能数据验证有效”，并给出下一步建议。

## 什么时候用哪种工具

- `perf.ps1`：做基线采集、回归对比、预算告警、HTML 报告。这是性能验收主入口，不能被单次热点列表替代。
- `ultimate-profile.ps1`：做 30 秒终极分析，一次运行同时生成 perf 与 Tracy 汇总，输出给 AI 看的 Markdown 和给人看的 HTML。
- `profile.ps1 -Mode tracy`：做交互式热点排查，适合查看线程并行、阶段重叠、尖峰帧发生时各线程在做什么。
- `profile.ps1 -Mode tracy-analyze`：做 Tracy 离线启发式分析，适合把 `.tracy` 自动导出为 CSV，再生成 txt 和 HTML 热点报告。

推荐顺序：

1. 先用 `perf.ps1` 确认是否真的退化，以及退化幅度。
2. 再用 `ultimate-profile.ps1` 或 `profile.ps1 -Mode tracy-analyze` 找出热点函数、线程竞争或尖峰来源。
3. 修改后回到 `perf.ps1` 做前后对比，不能只看单次 Tracy 结论。

## 终极分析模式

需要同时给 AI 和人工查看时，使用终极脚本：

```powershell
.\scripts\ultimate-profile.ps1
```

默认行为：

- 运行 30 秒 `presentation` 模式。
- 通过 Tracy-enabled 构建运行游戏，同时产出 `logs/performance.log` 与 `.tracy`。
- 生成 `logs/ultimate/ultimate-<timestamp>-ai.md`，供 AI 直接读取。
- 生成 `logs/ultimate/ultimate-<timestamp>-report.html`，供浏览器查看。
- 同时保留 perf 子报告、Tracy 子报告、性能日志快照与 trace 路径，方便追溯。

常用参数：

```powershell
.\scripts\ultimate-profile.ps1 -Seconds 30 -GameMode presentation
.\scripts\ultimate-profile.ps1 -Seconds 30 -GameMode exploration -Top 15
.\scripts\ultimate-profile.ps1 -OutputDir .\logs\ultimate -TraceKeep 2
```

终极报告解读顺序：

1. 先看 HTML 首页的平均帧、p95 / p99、超预算比例和埋点覆盖率。
2. 再看 `Perf Bottlenecks` 判断是否真的超过预算，以及主循环还是渲染阶段更可疑。
3. 再看 Tracy 输出定位具体 zone/function。
4. 给 AI 时优先提供 `*-ai.md`，不要只给截图。

## Tracy 模式

项目已支持通过环境变量开启 `tracing` 到 Tracy 的转发，脚本会自动设置：

```powershell
.\scripts\profile.ps1 -Mode tracy -Seconds 12 -GameMode presentation
```

说明：

- 运行前需要本机已安装 Tracy 桌面程序。
- 该模式会通过 `cargo run --features tracy-profile --bin dao_game` 启动专用 profiling 构建。
- 普通 `cargo run` 和 `.\scripts\perf.ps1` 不会启用 Tracy，避免影响日常开发和验收运行。
- 游戏启动后，打开 Tracy 并连接到本机运行中的进程。
- 该模式用于深度诊断，不会替代 `logs/performance.log` 和现有 HTML 对比流程。

## Tracy 自动分析模式

如果只需要直接拿到最有用的热点结论，优先使用自动分析模式：

```powershell
.\scripts\profile.ps1 -Mode tracy-analyze -Seconds 12 -GameMode presentation
```

该模式会执行完整闭环：

- 用 `cargo run --features tracy-profile --bin dao_game` 启动 Tracy-enabled 游戏。
- 用 `D:\windows-0.13.1\tracy-capture.exe` 捕获 `.tracy`。
- 用 `D:\windows-0.13.1\tracy-csvexport.exe` 导出 `*-summary.csv`、`*-self.csv`、`*-events.csv`。
- 用 `cargo run --bin tracy_analyze` 生成 `logs/tracy/<trace>-analysis.txt` 和 `logs/tracy/<trace>-analysis.html`。

CSV 含义：

- `*-summary.csv`：inclusive 总耗时汇总。
- `*-self.csv`：self time 汇总，用于过滤父级 wrapper span 干扰。
- `*-events.csv`：逐事件明细，用于计算 p50 / p90 / p95 / p99、尖峰和线程分布。

输出文件：

- `logs/tracy/<trace>-analysis.txt`：命令行友好的启发式结论。
- `logs/tracy/<trace>-analysis.html`：浏览器可视化报告，包含 source share、热点柱状图、线程负载和明细表。
- 自动捕获的 `.tracy` 文件会在 `logs/tracy` 内轮转，默认只保留最新 2 个；CSV、txt、HTML 报告不会随 trace 轮转自动删除。

分析已有 `.tracy` 文件时，不会重新启动游戏：

```powershell
.\scripts\profile.ps1 -Mode tracy-analyze -Trace D:\windows-0.13.1\test1.tracy -Top 8
```

常用参数：

```powershell
.\scripts\profile.ps1 -Mode tracy-analyze -Seconds 20 -GameMode exploration
.\scripts\profile.ps1 -Mode tracy-analyze -Trace .\logs\tracy\old.tracy -AnalysisOutput .\logs\tracy\old.txt -HtmlOutput .\logs\tracy\old.html
.\scripts\profile.ps1 -Mode tracy-analyze -TracyDir D:\windows-0.13.1 -CsvDir .\logs\tracy -Top 15
.\scripts\profile.ps1 -Mode tracy-analyze -TraceKeep 2
```

报告解读顺序：

1. 先看 HTML 的 `Most Useful Zones`，优先处理 self time 占比高、p99 高或 max/mean 尖峰明显的条目。
2. 再看 `Source Share`。如果热点主要在 dependency，优先回到项目层减少实体数量、渲染批次、Transform 层级或调度频率，不要直接修改依赖源码。
3. 再看 `Thread Event-Time Load`。线程耗时分布接近均匀时通常是并行工作量过大；单线程突出时优先排查串行 bottleneck 或主线程阻塞。
4. 最后回到 `perf.ps1` 做优化前后对比，不能只凭 Tracy 启发式报告宣布优化有效。

## 常用选项

```powershell
.\scripts\perf.ps1 -Seconds 20
.\scripts\perf.ps1 -Mode exploration
.\scripts\perf.ps1 -Output .\logs\my-report.html
```

只采集并打印报告：

```powershell
.\scripts\perf.ps1 -Action capture -Seconds 10
```

查看当前日志：

```powershell
.\scripts\perf.ps1 -Action report
```

对比当前和上一次：

```powershell
.\scripts\perf.ps1 -Action compare
```

只生成 HTML：

```powershell
.\scripts\perf.ps1 -Action html
```

对比指定两个日志：

```powershell
.\scripts\perf.ps1 -Action compare -Baseline .\logs\old.log -Candidate .\logs\new.log
```

输出 JSON：

```powershell
.\scripts\perf.ps1 -Action report -Json
```

## 瓶颈诊断能力

报告会输出 `bottlenecks` / `candidate_bottlenecks`，用于回答“瓶颈在哪里”：

- 帧预算问题：p95 是否超过 `frame_time_budget_ms`。
- 尖峰问题：p99 和 p50 差距是否过大。
- 主热点阶段：哪个阶段占据最多已埋点耗时。
- 尖峰阶段：哪个阶段 p99 明显高于平均值。
- 埋点覆盖率：已埋点阶段能解释多少平均帧时间。

如果报告提示 `low instrumentation coverage`，说明真实瓶颈可能在未埋点区域，需要继续给渲染准备、资源加载、启动流程或新系统补充埋点。

## 配置

`config/app.toml`：

```toml
performance_detail_interval = 1
frame_log_interval = 120
```

含义：

- `performance_detail_interval = 1`：每帧记录细粒度样本，适合性能分析。
- `performance_detail_interval = 0`：关闭逐帧细节样本。
- `frame_log_interval`：普通帧日志输出间隔，不影响细粒度 HTML 报告。
